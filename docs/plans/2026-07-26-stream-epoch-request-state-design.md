# Stream Epoch and Request Outcome Design

## Status

Accepted on 2026-07-26 as part of the approved seven-point production
hardening plan. The implementation uses a coordinated, stopped-and-drained
upgrade; mixed protocol versions are unsupported.

This design extends, rather than replaces, the accepted request deadline,
cancellation, idempotency, multi-Agent, and Connector database-decoupling
designs already present in this workspace.

## Problem statement

The current code is materially safer than the original tunnel implementation:

- Bridge creates separate logical request and transport-attempt IDs, propagates
  one absolute deadline, requires idempotency keys for mutating requests, and
  performs one unary Forward attempt.
- Agent keeps attempt-keyed pending guards, binds each pending request to an
  Agent-local Connector generation, expires heartbeat leases, rejects responses
  from the wrong local generation, and fails pending waiters when a session is
  removed.
- Connector cancels all queued/in-flight work when its stream ends and never
  owns durable database state.
- Agent owns a durable SQLite/PostgreSQL idempotency ledger. Completed results
  can be replayed; unresolved pending claims cannot be stolen automatically.

Those are preservation constraints. The remaining gaps are narrower:

1. The Agent-local generation is not carried on the wire, so Connector cannot
   validate that requests and cancels belong to its current stream incarnation.
2. Connector declares a tunnel up after the gRPC stream is created, without an
   explicit Agent registration acknowledgement.
3. Agent cannot distinguish locally queued, sent, and Connector-accepted
   attempts. Stream loss wakes waiters by closing a oneshot sender, which loses
   the phase and produces a generic channel-closed error.
4. Connector's active-attempt entry records cancellation but not request phase.
5. Connector cancellation on stream loss is correct, but dispatcher drain has
   no explicit upper bound before reconnect.
6. The existing durable `pending` idempotency state is safe but operationally
   under-documented: after possible dispatch it means outcome indeterminate,
   not permission to retry.

## Requirements

### Functional

1. Every Connector stream incarnation has an opaque, globally unique
   `stream_epoch` generated by Connector before registration.
2. Agent continues to use its local generation as the authoritative in-process
   fence and additionally validates the wire epoch.
3. Connector is not eligible for traffic until Agent has queued a matching
   registration acknowledgement.
4. Connector acknowledges an attempt only after it has reserved the attempt ID
   and successfully inserted the request into its bounded accept queue.
5. Agent records monotonic request phases `Queued -> Sent -> Accepted` and
   returns an explicit `StreamLost` outcome containing the last observed phase.
6. Stream loss never migrates or replays an old attempt onto a new stream.
7. Connector cancels old-epoch work and completes bounded shutdown before the
   next epoch is created.
8. Mutating operations retain the existing durable idempotency claim after any
   possibly dispatched outcome. No pending claim is auto-expired or stolen.

### Non-functional

- **Safety:** a message from an old stream cannot affect a pending request bound
  to another stream, even if an attempt ID is accidentally reused.
- **Availability:** stream loss wakes affected Agent handlers promptly and does
  not wait for the full request deadline or an unbounded Connector drain.
- **Security:** epoch values are validated, logged, and never trusted in place
  of the actual gRPC stream context or mTLS certificate binding.
- **Operability:** epoch values never appear as Prometheus labels; they are
  high-cardinality identifiers for structured logs only.
- **Compatibility:** Connector, Agent, Bridge, and generated protocol code are
  deployed as one stopped-and-drained release. Mixed live versions remain
  unsupported.
- **Scope:** no automatic cross-stream recovery, new database, new queue, or
  Connector durable-storage dependency.

## Chosen architecture

```mermaid
sequenceDiagram
    participant B as Bridge
    participant A as Agent
    participant C as Connector
    participant U as APISIX/upstream

    C->>A: Register(endpoint, connector, stream_epoch)
    A->>A: validate mTLS identity and epoch
    A-->>C: RegisterAck(stream_epoch)
    Note over A,C: session becomes eligible; Agent local generation remains authoritative

    B->>A: Forward(request_id, attempt_id, deadline, idempotency_key)
    A->>A: authorize, durable claim when mutating
    A->>C: ForwardRequest(..., stream_epoch)
    A->>A: phase = Sent; claim is now possibly dispatched
    C->>C: reserve attempt and enqueue
    C-->>A: ForwardAccepted(attempt_id, stream_epoch)
    A->>A: phase = Accepted
    C->>U: HTTP request with remaining deadline and idempotency key
    U-->>C: HTTP response
    C-->>A: ForwardResponse(attempt_id, stream_epoch)
    A->>A: validate source generation + wire epoch; persist completed result
    A-->>B: response

    Note over A,C: on stream loss, Agent fails only that generation; Connector cancels only that epoch
```

### Protocol additions

`stream_epoch` is a UUID string, not a shared monotonic counter. Ordering is not
required; fencing requires uniqueness and equality. A durable distributed
counter would add coordination without improving the selected fail-fast model.

Add these fields without changing existing tag numbers:

```proto
message ConnectorRegister {
  // existing fields 1..4
  string stream_epoch = 5;
}

message ConnectorHeartbeat {
  // existing fields 1..3
  string stream_epoch = 4;
}

message ForwardRequest {
  // existing fields 1..9
  string stream_epoch = 10;
}

message ForwardResponse {
  // existing fields 1..6 (`header_values` already owns field 6)
  string stream_epoch = 7;
}

message CancelRequest {
  // existing fields 1..3
  string stream_epoch = 4;
}

message ConnectorRegisterAck {
  string connector_id = 1;
  string endpoint = 2;
  string stream_epoch = 3;
}

message ForwardAccepted {
  string request_id = 1;
  string attempt_id = 2;
  string stream_epoch = 3;
}
```

Add `register_ack` and `accepted` as new `TunnelMessage` variants. The direction
is strict: Register/Heartbeat/Response travel Connector to Agent;
RegisterAck/Request/Cancel travel Agent to Connector; ForwardAccepted travels
Connector to Agent. Any message sent before registration or in the wrong
direction closes that stream as a protocol violation.

### Agent state and fencing

`OutboundEntry` stores both the Agent-local `generation` and Connector-supplied
`stream_epoch`. The local generation comes from the actual gRPC handler and is
the authoritative source fence. Payload epoch equality is an additional
end-to-end invariant, not a replacement.

`PendingEntry` becomes:

```rust
enum PendingPhase {
    Queued,
    Sent,
    Accepted,
}

enum PendingFailure {
    StreamLost {
        phase: PendingPhase,
        stream_epoch: String,
    },
    ProtocolViolation {
        phase: PendingPhase,
        reason: String,
    },
}
```

The pending oneshot carries `Result<ForwardResponse, PendingFailure>`. Phase
transitions are monotonic so a very fast acknowledgement cannot be overwritten
by the sender later recording `Sent`. Registration cleanup drains only entries
whose endpoint, local generation, and epoch all match, and sends an explicit
failure before dropping them.

The Agent queues `RegisterAck` before publishing the new session into the
registry. FIFO ordering on the Agent outbound channel guarantees Connector sees
the acknowledgement before any request selected through that registry entry.

An absent `ForwardAccepted` is never treated as proof that a mutating operation
did not execute: the acknowledgement itself may have been lost. Once the Agent
successfully queues a request to the stream, the durable idempotency claim stays
pending until a definitive response is persisted.

### Connector state and shutdown

Connector generates a fresh UUID for every `run_tunnel_once`, includes it in
Register and Heartbeat, and waits for a matching RegisterAck before setting the
tunnel-up gauge or accepting requests. Every Request and Cancel must carry the
same epoch. Every Accepted and Response echoes it.

The current `CancelState` is extended with a monotonic phase:

```text
Reserved -> Accepted -> Executing -> Completed
                       \-> Cancelled
```

`ForwardAccepted` is emitted only after the active-attempt reservation and
bounded queue insertion succeed. Queue-full and deadline rejection remain
ordinary terminal responses and are not acknowledged as accepted work.

When the stream ends, Connector cancels all states for that epoch, closes the
accept queue, and waits at most `SAG_CONNECTOR_STREAM_DRAIN_TIMEOUT_MS` (default
2000 ms) for the dispatcher. On expiry it aborts the dispatcher and reconnects.
Cancellation cannot roll back a business transaction that already committed;
the Agent idempotency claim therefore remains unresolved.

### Error and retry semantics

The selected policy is fail-fast, not resume:

- Agent stream loss returns gRPC `Unavailable` immediately with metadata
  `x-sag-outcome: unknown`, the attempt ID, and the stream epoch.
- Bridge preserves this as an HTTP error response and never retries the logical
  request inside the same ingress call.
- A read-only caller may issue a new logical request according to caller policy.
- A mutating caller must reuse the same idempotency key. Completed operations
  replay; unresolved pending operations remain blocked for reconciliation.
- Neither `Sent` nor missing `Accepted` grants permission to release a durable
  mutation claim.

This provides at-most-once gateway dispatch plus replay of known results. True
exactly-once business effects still require the downstream service to honor the
propagated idempotency key.

## Alternatives rejected

### Keep only the Agent-local generation

The current local fence already prevents many stale-response bugs, but it does
not provide Connector-visible epoch validation or an explicit ready handshake.
It is retained as the inner fence but is no longer the whole contract.

### Resume old requests automatically on a new stream

Rejected. It requires a durable replay log, acknowledgement recovery, status
queries, and a downstream idempotency contract. It would turn a bounded tunnel
hardening change into a message-delivery subsystem.

### Add another idempotency database

Rejected. `shared_storage::IdempotencyStore` already provides the authoritative
Edge ledger. The change strengthens its documented state semantics and tests;
it does not create a competing store or reconnect Connector to PostgreSQL.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Wire fields are additive but semantics differ | Stop ingress, drain, and deploy all protocol participants as one release |
| Ack is lost after Connector accepted work | Treat every locally sent mutation as possibly dispatched; never release its claim based on missing ack |
| Old stream sends forged current epoch | Validate actual Agent-local generation as well as payload epoch |
| Epoch cardinality overwhelms metrics | Put epoch only in structured logs, never metric labels |
| Connector dispatcher hangs during old-stream drain | Apply a 2-second configurable drain bound, then abort |
| Downstream committed before cancellation | Preserve the durable pending claim and report outcome unknown |
| Concurrent workspace work changes the baseline | Implementation starts with a source-shape guard and stops on incompatible drift |

## Success criteria

1. A Connector is not eligible or reported up before matching RegisterAck.
2. Old heartbeat, acknowledgement, response, or cancel messages cannot affect a
   new stream with the same logical endpoint.
3. Dropping one of multiple Connector sessions fails only attempts assigned to
   that session; other sessions remain healthy.
4. N pending attempts on a lost session are failed promptly with explicit phase
   and outcome instead of consuming the request deadline.
5. Connector old-epoch tasks are cancelled and drain is bounded to 2 seconds by
   default; no task or response is migrated to the new epoch.
6. Bridge performs no automatic retry and exposes an `unknown` outcome.
7. Mutating stream-loss tests leave the durable claim pending; completed results
   still replay and conflicts still reject.
8. Focused tests, workspace checks, static protocol guards, fault injection, and
   coordinated Compose rendering pass in an environment with a working linker.

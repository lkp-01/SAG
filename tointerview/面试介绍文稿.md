## 面试补强：结果、存储和我的贡献

### 1. 结果：我不只把链路做出来，也做了压测验证

我在 MVP 阶段做了 k6 压测，验证的不是单个接口，而是从登录、身份校验、策略判断到隧道转发的整条链路。

在一组严格的全链路稳态测试里，目标是每秒 120 次完整业务迭代；实际完成了 10,198 次迭代、40,792 次 HTTP 请求，登录、身份校验、策略判断和数据面转发的成功率都是 100%，整体请求 P95 大约是 101ms，没有出现 dropped iterations。这个结果至少证明了 MVP 的基础闭环可以稳定跑通，不是只把页面和接口拼在一起。

我也对数据面单独做过 3,000 到 7,000 QPS 的容量爬坡，路径是边缘入口、Bridge、Agent、Connector、APISIX 到内网 Mock 服务。在 3,000 QPS 的档位，实际达到约 2,904 次/秒，路由可达率 97.19%，P95 是 24.4ms；在 5,000 QPS 的档位，实际约 4,822 次/秒，路由可达率 94.08%，P95 是 54ms。

这里我会主动说明口径：这组容量测试的“路由成功”指请求已经经过隧道并到达 APISIX，包含上游业务返回 5xx 的情况，所以它用于验证网关链路的容量和可达性，**不能直接说成 5,000 QPS 的业务成功率**。面试开场我重点讲前一组严格全链路结果；这组大压测留给技术面追问，反而能说明我知道怎么正确解读压测数据。

**可直接说：**

> 这个 MVP 做完后，我没有只停在功能能跑的层面，还做了全链路压测。在每秒 120 次完整访问的稳态测试下，登录、鉴权、策略和内网转发的成功率都是 100%，P95 大约 101 毫秒。后面也做了数据面容量爬坡，验证了网关链路在更高并发下的可达性和瓶颈位置，所以这个项目最终不仅验证了自建方案能跑通，也有一套可以继续优化的性能基线。

### 2. 共享与存储层：不只是一段 SQLite 初始化

这里不建议再说“存储面就是消息定义和 SQLite 初始化”，因为消息定义和持久化其实是两个职责。我的说法会改成：项目有一个共享与存储层。共享部分定义了 Bridge、Agent 和 Connector 之间的 gRPC 消息协议，保证几段服务对请求、响应和关联 ID 的理解一致；存储部分把用户、策略、应用、API 路由、隧道路由、内网目标、审计记录和基础指标持久化下来。

在 MVP 阶段，系统支持用 SQLite 做轻量部署，便于快速启动和验证；同时封装了 PostgreSQL 的切换能力，后续部署时不需要重写上层业务逻辑。这样做的目的不是为了“用了两个数据库”，而是让 MVP 先低成本落地，同时给后面的正式部署留好扩展路径。

**可直接说：**

> 存储这一层我做得不只是 SQLite 初始化。共享部分先定义了服务之间的 gRPC 协议；持久化部分负责保存用户、权限、路由、应用和审计等配置。MVP 阶段可以先用 SQLite 轻量部署，后面也预留了切换 PostgreSQL 的能力，所以它既适合快速验证，也不会把后面的部署路径锁死。

这个项目我不是只负责 Agent、Bridge 或前端里的某一个模块，而是在 AI 协同开发的方式下，完成了整个 MVP 的端到端实现。我负责把业务目标拆成架构和模块边界，再把前端管理端和用户门户、认证和策略服务、控制面、Bridge、Agent、Connector、APISIX 路由、存储、Compose 部署、监控和 k6 压测接成一个完整闭环。

## 2 分钟版本：先让 HR 听懂

我做的项目叫 Secure Access Gateway，也就是一个面向企业内网应用的安全访问网关。

它要解决的问题很实际：公司内部的 OA、研发平台或业务后台，不能直接暴露在公网；但员工、合作方或者外部系统又确实需要在受控条件下访问。传统做法往往是单独开端口、配 VPN，管理和审计都比较分散。这个项目把身份认证、访问权限、内网转发和管理运营放到一条链路里统一处理。

我主要围绕这条链路做了几个部分。第一是管理和用户侧：管理员可以配置应用、路由、用户和权限，普通用户则在门户里查看自己能访问哪些服务。第二是认证和授权：用户登录后拿到令牌，系统再根据“谁访问哪个应用、什么路径”判断是否允许访问，默认是不放行。第三是最核心的内网访问链路：外部请求先到网关，再通过受控的长连接转到部署在内网侧的 Connector，最后由内网网关转发给真实业务服务。这样业务服务不用直接暴露在公网。

技术上，后端核心服务主要用 Rust，实现并发处理和隧道通信；服务之间使用 HTTP 和 gRPC；前端采用 Next.js 和 React；数据存储支持 SQLite 和 PostgreSQL，Redis 主要用于登录状态和缓存；另外接入了 Prometheus、Grafana 做基础监控。 

我在做这个项目时最关注的不是“把链路打通”就结束，而是让它可管理、可观察、可降级：例如策略默认拒绝、隧道健康检查、路由变更同步，以及审计和指标记录。做完 MVP 后，我还做了严格的全链路压测：每秒 120 次完整访问下，登录、鉴权、策略和内网转发成功率都是 100%，P95 大约 101ms。这个项目也是我在 AI 协同下完成的端到端 MVP，让我比较完整地实践了从前端配置，到控制面管理，再到内网数据转发的一套安全接入思路。

**记忆骨架：** 问题是“内网不能裸露”；方案是“认证 + 策略 + 隧道”；我的工作是“控制台、权限、转发链路”；价值是“安全、可管、可查”。

## 5 分钟版本：适合技术面第一轮

我介绍一下 Secure Access Gateway，简称 SAG。它是一个企业内网应用的安全接入项目，目标不是简单做一个反向代理，而是让外部访问内网应用时，经过身份确认、权限判断、受控转发和审计记录，避免直接把业务系统暴露到公网。

项目的出发点是：企业里常见的 OA、研发平台、运营后台，很多都在内网。访问需求一多，如果靠开端口、临时白名单或分散 VPN 来处理，权限容易失控，运维也很难回答“谁在什么时候访问了哪个应用”。所以我把系统按控制面和数据面来拆。

控制面负责“管什么、谁能访问”。这里有管理控制台、用户门户、认证服务、策略服务和控制面服务。管理员可以维护用户、身份源、角色映射、应用和路由；用户侧可以登录并看到自己有权限的服务。认证服务负责用户名密码登录、令牌签发，也可以对接 OIDC 或 4A 一类的外部身份源。策略服务则根据用户、应用和路径做判断；我采用了默认拒绝的思路，只有命中允许规则的请求才能继续往下走。

数据面负责“请求怎么安全到达内网”。请求进入边缘后，会先由 HTTP Bridge 做协议适配和请求限制，再转成 gRPC 请求交给隧道 Agent。Agent 根据应用标识找到对应的内网 Connector。Connector 是主动从内网发起连接的，接到请求后再交给 APISIX 路由到真实的内部服务。这样外部没有必要直接连接业务服务，内网侧也可以按应用隔离访问链路。

我在实现时比较关注三类问题。

第一是可靠性。隧道不是只建连就够了，我增加了 Connector 注册、心跳和健康检查的处理；路由变更由控制面维护并同步给 Agent。对于请求体大小、并发和超时也做了边界控制，避免单个异常请求拖垮转发服务。

第二是安全性。认证、策略和隧道是三层不同的职责：认证回答“你是谁”，策略回答“你能不能访问”，隧道负责“让请求如何进入内网”。服务间的 gRPC 可以启用双向 TLS；敏感配置通过环境变量注入；同时保留审计记录。需要说明的是，这些安全能力也依赖正确的部署配置，开发环境的默认值不能直接等同于生产安全基线。

第三是可运维性。项目提供管理控制台和门户，数据层同时兼容 SQLite 与 PostgreSQL；Redis 用于部分会话和缓存场景；再通过 Prometheus、Grafana 和 OpenTelemetry 提供指标采集和链路观察。这样当访问失败时，可以按“认证、策略、隧道、内网路由”这条路径定位，而不是只看到一个 502。

技术栈方面，后端核心服务用 Rust，重点利用它在并发网络服务和资源控制上的优势；通信主要是 HTTP 与 gRPC；前端是 Next.js/React；内网七层路由使用 APISIX；存储使用 SQLite 或 PostgreSQL，并配合 Redis。 

这个项目对我最大的收获，是不只从单个服务出发，而是从完整访问链路出发做设计：既保证业务服务不裸露，也让权限、路由和运营状态有统一的管理入口。MVP 完成后，我用 k6 做了严格全链路压测：120 次完整访问/秒下，链路成功率 100%，P95 约 101ms。我是在 AI 协同开发的方式下完成这个端到端 MVP 的，AI 帮助提升实现和排查效率，但架构、集成、压测验收和最终交付由我负责。后续如果继续产品化，我会优先完善多实例状态共享、端到端自动化测试、生产证书轮换和告警闭环。

**记忆骨架：**

1. 场景：内网应用需要被安全访问。
2. 拆分：控制面负责“管”，数据面负责“通”。
3. 链路：登录 → 策略 → Bridge → Agent → Connector → 内网服务。
4. 重点：可靠性、安全性、可运维性。
5. 收尾：目前能力 + 下一步产品化方向。

## 10 分钟版本：适合项目深挖

我想介绍的项目是 Secure Access Gateway，简称 SAG。它的定位是企业内网应用的安全接入网关。通俗说，就是让外部用户或外部系统在需要访问内网业务时，不是直接碰到业务服务器，而是先经过一套统一的身份认证、权限判断和受控转发链路。

### 1. 为什么做这个项目

企业内部通常有很多不适合直接暴露到公网的系统，比如 OA、研发平台、运营后台，或者只允许特定角色调用的 API。现实中的难点并不只是“把请求转进去”，而是几个问题要一起解决：

1. 访问者是谁，身份是否可信；
2. 他能访问哪个应用、哪一类接口；
3. 内网服务怎样不开放公网入口也能被访问；
4. 管理员怎样配置、审计和排障。

SAG 的思路是把这些问题收束成一条访问链路：先确认身份，再做权限判断，然后通过隧道进入内网，最后把访问结果和运行状态记录下来。它不是要替代所有企业安全产品，而是提供一个可落地的安全接入原型和管理框架。

### 2. 整体怎么拆

我把系统分成控制面和数据面。

控制面解决“谁能访问什么，以及怎么配置”。它包括三个主要服务：

- 认证服务：负责账号登录、令牌签发和校验，并支持对接 OIDC 或企业 4A 这类外部身份源；
- 策略服务：根据用户、角色、应用标识和路径前缀做允许或拒绝的判断；
- 管理服务：维护应用、API 路由、隧道路由、内网目标、审计和运行指标，并提供给管理控制台使用。

前端分成管理员控制台和用户门户。管理员配置应用、用户、身份源、路由和策略；普通用户只看到自己可访问的服务。这样“配置的人”和“使用的人”在界面和权限上都是分开的。

数据面解决“请求怎样进入内网”。主链路可以概括成：

```text
外部请求
  → 边缘入口 / HTTP Bridge
  → 隧道 Agent
  → 内网 Connector
  → APISIX
  → 真实内部业务服务
```

其中 Connector 部署在内网侧，它主动和 Agent 建立长连接。外部请求到来后，Agent 根据应用标识选择一个健康的 Connector，再把请求沿现有隧道发过去。Connector 收到请求后，通过内网 APISIX 访问真实上游。这样业务服务只需要接受来自内网网关的流量，不需要直接对外开放。

### 3. 我重点完成和关注的部分

第一个重点是把“认证、授权、转发”拆清楚。

认证只解决“你是谁”。登录成功后，系统发放令牌，后续请求携带令牌完成身份校验。授权则解决“你有没有权限”。策略规则围绕主体、应用和路径来匹配，并采用默认拒绝的原则。也就是说，认证成功不等于拥有所有访问权限。隧道转发只解决“允许后的请求如何安全进入内网”。这三个职责如果混在同一个服务里，后续新增身份源、增加策略规则或排查访问失败都会很难维护。

第二个重点是数据面链路的边界控制。

HTTP Bridge 不是简单地把 HTTP 改成 gRPC。它会处理请求体大小、超时、必要头部和部分连接级头部的清理，再把请求组织为统一的转发消息。Agent 维护 Connector 的注册、心跳和健康状态；只有符合路由和健康条件的连接才会被选中。Connector 侧也会控制并发和接收队列，避免某个慢请求无限占用资源。对于可选的过载场景，Bridge 可以借助 Redis Stream 做排队和结果轮询，但这属于按部署需求开启的能力，不是所有环境都会默认使用。

第三个重点是配置和运行状态的管理。

路由、应用和审计等信息由共享存储管理，开发或轻量环境可以使用 SQLite，部署环境可以切到 PostgreSQL。控制面维护路由后，Agent 会按周期拉取并更新本地路由表；如果配置了 APISIX Admin API，也会尝试同步相应的网关路由。这里我会特别说明一个工程取舍：控制面自身的配置写入和向 APISIX 的同步不是一个强一致分布式事务，所以同步失败要有明确告警、重试或对账机制，不能假设“配置保存成功就代表流量一定已经切换”。

第四个重点是前端和可观测性。

管理员控制台不仅用于配置，也用于查看应用、路由、身份源、审计、故障和运行指标；用户门户面向普通用户展示可访问服务和预检结果。后端暴露基础指标，再接入 Prometheus、Grafana 和 OpenTelemetry。排障时可以按链路逐段检查：是不是没有登录、策略是否拒绝、目标 Connector 是否在线、路由是否同步、内网上游是否健康。这样的设计比只在最后返回一个错误码更有可操作性。

### 4. 技术选型怎么向面试官解释

后端核心服务选择 Rust，是因为这个项目包含多段网络转发、连接管理和并发处理，Rust 对资源控制和高并发网络服务比较合适。服务对外接口主要用 HTTP，内部转发使用 gRPC：HTTP 方便前端和管理接口调用，gRPC 更适合内部的强类型消息和长连接通信。

前端使用 Next.js 和 React，便于快速构建管理控制台和用户门户。内网七层路由选择 APISIX，让 Connector 不直接耦合具体业务服务。数据层支持 SQLite 和 PostgreSQL，降低本地开发与部署环境的切换成本；Redis 主要承担登录状态、策略缓存以及可选的过载队列。可观测性采用 Prometheus、Grafana 和 OpenTelemetry，分别覆盖指标采集、展示和链路数据接入。

我不会把这些技术名词当作项目价值本身。真正的价值是：每个技术组件都有清晰职责，认证管身份、策略管权限、隧道管网络可达、APISIX 管内网路由、控制台管配置和运营。

### 5. 遇到的工程难点与取舍

我认为这个项目最关键的难点有三个。

第一，内网访问既要可达又不能失控。Connector 主动出站建连，减少了业务服务暴露的需要；但这不等于系统天然绝对安全，生产上仍需要正确配置证书、网络边界、密钥轮换和入口防护。

第二，实时性和一致性的平衡。Agent 使用本地的 Connector 注册与路由状态，有利于低延迟转发；但如果要做多实例高可用，就不能只依赖单进程内存，需要引入共享注册或明确的分片与故障切换方案。

第三，功能完整与可验证性。项目已经覆盖了核心链路、管理页面、基础监控和多种 Compose 部署形态，但生产级交付还需要补强端到端自动化测试、前端 E2E、CI、告警闭环，以及完整的证书和密钥治理。这些是我在设计和复盘时会主动说明的边界，而不是把原型能力直接包装成生产承诺。

### 6. 结果与收获

最终，这个项目把一个比较分散的内网访问问题，整理成了可以配置、可以观察、可以扩展的闭环：管理员配置应用和权限，用户完成登录，系统完成策略判定，请求通过受控隧道进入内网，随后可以从审计和指标里追踪整个过程。MVP 的严格全链路压测在 120 次完整访问/秒下实现了 100% 成功率、P95 约 101ms；数据面容量测试也沉淀了 3,000 到 7,000 QPS 的链路可达性和瓶颈数据。

对我来说，最大的收获是学会从“完整访问链路”而不是“单个接口”看问题。这个 MVP 是我在 AI 协同开发的方式下端到端完成的：我负责把业务目标、模块边界、服务集成、部署和压测验收收口。做安全接入时，功能打通只是起点；权限边界、失败路径、运维入口和生产限制，都需要在设计阶段一起考虑。

**记忆骨架：**

1. 背景：内网系统不能裸露，但要被受控访问。
2. 架构：控制面管配置和权限，数据面管请求转发。
3. 流程：身份认证 → 策略判断 → Bridge → Agent → Connector → APISIX → 业务。
4. 亮点：职责拆分、健康与限流、配置同步、可观测性。
5. 取舍：默认拒绝、主动出站、最终一致、多实例待补强。
6. 收尾：安全接入是一条完整链路，不是一次代理转发。

## 高频追问：一句话接住，再按需展开

| 面试官可能问 | 可先这样回答 |
| --- | --- |
| 这个项目和普通反向代理有什么不同？ | 反向代理主要解决流量怎么转发；SAG 在转发前增加了身份、策略、内网隧道和统一管理，把“能不能访问”和“怎么访问”同时处理。 |
| 为什么要用 Connector？ | Connector 由内网主动建连，外部请求复用这条受控链路进入内网，业务服务不需要直接暴露公网入口。 |
| 为什么 HTTP 还要转成 gRPC？ | 对外保留 HTTP 的通用性；内部用 gRPC 传递结构化转发消息并管理长连接，更适合这条隧道链路。 |
| 权限怎么控制？ | 先认证身份，再按用户或角色、应用和路径匹配策略；默认拒绝，只有命中允许规则才放行。 |
| 你怎么看这个项目的不足？ | 当前的单实例内存状态、配置同步的最终一致性，以及端到端自动化测试和生产密钥治理，都需要继续补强。 |
| 你个人最大的收获？ | 学会把安全、网络、管理和运维放到一条真实访问链路里考虑，而不是只把某一个接口做通。 |
